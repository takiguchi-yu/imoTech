# M10: 記事に「使いどころ」を付ける

紹介した技術が**誰のどんな場面で効きそうか**を記事に足す。

**Status:** 完了
**Blocked by:** なし（M6 で用語を足した経路をなぞる）

## なぜやるか

要旨（元記事が何を言ったか）と論調（反応で何が言われたか）だけでは、
読者が「で、自分はこれをどう使えるのか」に辿り着けない。

## 設計上の最大の論点 — 既存の規約と衝突する

`prompts/compose.md` の「守ること」は、これまで次の 2 つを課していた。

> 4. **事実と意見を混ぜない。** 元記事が述べたこと、反応で述べられたことだけを書き、
>    あなた自身の評価や結論を加えないでください。
> 6. 元記事や反応に書かれていないことを補わないでください。

「どう活用できそうか」は**推測**なので、この 2 つと正面から衝突する。

**ユーザーの判断: LLM に応用先を考えさせる**（元記事に書かれていない応用案も書かせる）。
そのうえで次の 3 つで担保する。

1. **例外は `use_cases` だけ**とプロンプトに明記する（4 と 6 の両方に書き、
   `use_cases` の指示にも「他のフィールドでは引き続き禁止」と重ねる）
2. **推測であることを但し書きで示す**（`render.USE_CASE_NOTE`）。公開記事と
   Notion のレビュー面の両方に出す。**文言は 1 か所に閉じる** —
   2 つで違うことが書いてあると、どちらが正か分からなくなる
3. **`site/src/pages/about.astro` の開示表に 1 行足す**。imoTech は
   「何を機械がやり、何を人間がやるか」を読者に開示しているので、
   この節だけ性格が違うことを表と本文の両方で説明する

## 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| 節の名前 | `## 使いどころ` | |
| 置き場所 | **論調の後、imo の前** | 機械が書く部分（要旨・論調・使いどころ）をまとめ、そのあとに運営者の imo が来る |
| 件数 | **0〜3 件** | 主張・意見の記事には使いどころが無い。数を埋めさせると一般論が並ぶ |
| 長さ | `scene` 20〜40 字 / `detail` 60〜120 字 | |
| 値の形 | `models.UseCase(scene, detail)` | `GlossaryEntry` と同じ 2 フィールドにして、記事の見た目を `- **場面**: 説明` に揃える |
| 既存記事 | **触らない** | M6（用語）と同じ扱い。新しい記事から付く |

**見送った設計**: `GlossaryEntry` と `UseCase` の共通基底。フィールド名が違うだけの値で
振る舞いを持たないので、抽象化するとかえって読みにくい（`oo-design` の YAGNI）。
Markdown の行の正規表現だけは共用した（`_LABELED_LINE_RE`）。

## 実データでの確認（2026-09-23）

本番の候補ストア・記事ディレクトリ・Notion に触れずに 3 本生成した。

| 記事 | 種類 | 使いどころ |
|---|---|---|
| 「Sun 失敗の本質は『日常業務への飽き』か」 | 歴史の振り返り・意見 | **0 件**（見出しごと出ていない）|
| 「AI 生成物の不可視透かしを『スパイマーク』と呼ぶ提案」 | 提案・議論 | 1 件 |
| 「Transformer の視覚的解説ツールが話題」 | ツール紹介 | 2 件 |
| 「生成AI を使ったら著作権侵害になる？」（Qiita） | 解説 | **0 件** |

**文字数は 3 件とも指定範囲内**（`scene` 23 / 24 / 33 字、`detail` 98 / 86 / 69 字）。

生成された例:

> - **社内勉強会でTransformerの仕組みを非専門家に解説するとき**: GPT-2の重みを使って実際に推論が動く様子を画面上で提示できるため、注意機構がどの単語に注目しているかを視覚的に示しながら解説できます。

`scene` が「誰が何をしようとしているか」になっており、`detail` が
**元記事のどの性質がそれを可能にするか**（GPT-2 の重みで実際に動く）を含んでいる。
禁じた一般論（「AI なので幅広い用途に使えます」）は出ていない。

## 申し送り

- **既存の 12 記事には付かない。** 新しく生成した記事から付く（M6 と同じ）
- **「使いどころ」の質は記事の種類に左右される。** ツール・モデルの紹介では具体的に書けるが、
  主張・意見の記事では 0 件になる。実測で 4 本中 2 本が 0 件だった。これは設計どおりだが、
  「使いどころが付く記事」と「付かない記事」が混在することになる
- **外れた応用案が出る可能性は残る。** 但し書きと `about` での開示で対処しているが、
  実際に的外れなものが出たら、プロンプトの禁止例を増やすのが次の手

### Major

| 指摘 | 直したこと |
|---|---|
| **記事ページ末尾の開示文が各節を名指しで列挙していて、使いどころだけが漏れていた。** 「列挙されていない節＝運営者が書いた／元記事由来」と読める — **唯一の推測の節が開示の列挙からだけ漏れる**という最悪の並びで、`about.astro` を直した効果を記事ページ側で打ち消していた | **列挙をやめた。** 「imo 以外は生成 AI による生成」+「『使いどころ』の節がある記事では、そこに元記事に書かれていない応用案が含まれます」。節が増えても列挙漏れが起きない形にした |
| **但し書きが手編集で消えても、どの経路も検知しない。** `from_markdown` は但し書きの有無に関係なく項目を読み戻し、サイトのゲート（`imo.ts`）は imo しか見ないので、ビルドもテストも通って公開に至る | `render.ensure_use_case_note()` を足し、**公開の直前（`cmd_publish`）で補う**（冪等）。手で消しても戻る |
| **件数と文字数がコード側で一切制限されていない。** スキーマの `maxItems` はプロバイダ側の努力目標で、フォールバック先のモデルほど守らない。実測で 6 件返すと 6 件通り、`detail` 3000 字で Notion の 1 件が 6 ブロックに割れた | `_labeled_pairs()` に件数と長さの上限を入れた。**`_to_glossary` も同じ穴を持っていたので共通化**して両方守るようにした |
