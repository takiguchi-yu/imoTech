# M12: アイキャッチ（OG 画像）を差分だけ描く

**Status:** 未着手（いまは困っていない。閾値に近づいたら着手する）
**Blocked by:** なし

## なぜやるか

アイキャッチはビルドのたびに**公開記事の全件を描き直している**（M11）。1 本あたり約 0.3 秒
（1 本目だけフォントの読み込みで約 0.7 秒）なので、公開記事が増えるほどビルドが長くなる。

公開ワークフロー（`.github/workflows/publish.yml`）は `timeout-minutes: 10` で、毎時動く。
ビルドが 10 分を超えると、**承認済みの記事が毎時失敗し続けて公開されない**。

## 見つけたときの状況

M11 のリスクレビューで指摘された。実測と計算:

| 公開記事の本数 | 画像の生成にかかる時間（概算） |
|---|---|
| 1（2026-09-23 時点） | 約 0.7 秒 |
| 100 | 約 30 秒 |
| 1,000 | 約 5 分 |
| **1,500** | **約 7.5 分** — `npm ci`・publish・デプロイを足すと 10 分に近づく |

記事の生成は 3 日で 12 本、そのうち公開済み（imo 記入済み）は 1 本。**公開のペースしだいで、
1 年以上先に閾値に届く**。いま直さないのは、キャッシュの仕組み（何を鍵にするか、どこに置くか）の
複雑さに見合う問題がまだ起きていないため。

## 完了条件

- [ ] タイトル・ソース・注目度・カードのデザイン・フォントのいずれかが変わった記事だけを描き直す
  （鍵はこれらの値のハッシュ。デザインやフォントを変えたら全件描き直しになること）
- [ ] 前回のビルドの画像を GitHub Actions のキャッシュ（`actions/cache`）か、それに代わる場所に置く
- [ ] キャッシュが無いとき（初回・消えたとき）は全件描いて、結果は今と同じになる
- [ ] 公開記事 1,500 本相当でビルドが 10 分に収まることを、ダミーの記事で確かめる
- [ ] `site/scripts/check-og.mjs` と `check-unpublished.mjs` が引き続き通る
  （**未公開記事の画像がキャッシュから紛れ込まない**こと。キャッシュを使うと、過去に公開して
  いまは取り下げた記事の画像が残りうる）

## 着手できる条件

- 公開ワークフローのビルドのステップが **5 分を超えた**とき（Actions の実行時間で見る）
- または、公開記事が **700 本**を超えたとき

## 申し送り

- **取り下げた記事の画像が残る**のがキャッシュの一番の落とし穴。いまは毎回すべて描き直すので、
  取り下げれば画像も消える。キャッシュを入れたら、公開記事の集合に無い画像を必ず捨てること
